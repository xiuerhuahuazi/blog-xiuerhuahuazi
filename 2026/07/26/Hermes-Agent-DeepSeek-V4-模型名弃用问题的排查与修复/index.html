第三步：找到原因

DeepSeek 在 2026 年 7 月 24 日 正式弃用了旧模型名：

旧模型名（已弃用） 新模型名
deepseek-chat deepseek-v4-flash（非思考模式）
deepseek-reasoner deepseek-v4-flash（思考模式）或 deepseek-v4-pro

弃用时间正好是我们配置后就发生的——7 月 23 日部署，7 月 24 日 23:59 弃用生效。所以之前能用，几天后就不能用了。

Hermes 的 model_normalize.py 还在用旧名称 deepseek-chat，导致：

  1. 用户配置 deepseek-v4-flash → 被 normalize 为 deepseek-chat
  2. deepseek-chat 发送到 DeepSeek API → DeepSeek 返回 400 说这个模型名不支持

根本原因总结

这是一个典型的 Provider 端 Breaking Change 未被适配端同步 的问题：

本质上是一个硬编码的映射表过时了。model_normalize.py 将"所有 DeepSeek 模型"强制映射到一个固定值，这个设计在 API 稳定时没问题，但一旦上游改了模型名，就会产生矛盾。

启示

  1. LLM Provider 的模型名不是稳定的 API 契约。DeepSeek 用了一年多的 deepseek-chat 说弃就弃了。
  2. 自动 normalize 逻辑要谨慎。好心帮你"统一名称"的逻辑，在 API 变更时会先于用户配置出错。
  3. Docker 容器内的 Python 代码可以直接修。docker exec + sed 是临时修复的有效手段，但要等上游发新镜像才能永久解决。
  4. 看日志第一行很重要。Normalized model ... to ... 这个看似无害的日志，其实直接暴露了问题所在。
