Hermes Agent 接入 DeepSeek V4：模型名弃用问题的排查与修复

接入 DeepSeek V4 时被模型名弃用卡住：从报错、配置文件到最终可用配置的排查过程。

目录

  1. 背景
  2. 排查过程
  3. 修复方法
  4. 根本原因总结
  5. 启示
  6. 附录：DeepSeek V4 新模型名

日期：2026-07-26

环境：UGREEN DXP4800PLUS-120 NAS + Docker (ugreen/hermes-agent:v1)

模型：DeepSeek V4 Flash

背景

我在 UGREEN NAS 上部署了 Nous Research 的 Hermes Agent 作为家庭 AI 助手。它通过 OpenRouter 风格的 provider 机制接入各种大模型。我将默认模型从 OpenRouter 的 Claude 换成了 DeepSeek，配置如下：

# ~/workplace/config.yaml
model:
  default: deepseek-chat
  provider: deepseek
  base_url: https://api.deepseek.com

之前一切正常。但几天后，当我再次对话时，收到了这个错误：

⚠️  Normalized model 'deepseek-v4-flash' to 'deepseek-chat' for deepseek.
⚠️  API call failed (attempt 1/3): BadRequestError [HTTP 400]

   📝 Error: HTTP 400: The supported API model names are deepseek-v4-pro
      or deepseek-v4-flash, but you passed deepseek-chat.

现象很矛盾：模型名写成 deepseek-chat 它报错不支持，写成 deepseek-v4-flash 又被自动"修正"回 deepseek-chat。

排查过程

第一步：查看错误日志

关键信息在日志开头：

Normalized model 'deepseek-v4-flash' to 'deepseek-chat' for deepseek.

这说明 Hermes 内部有一个模型名规范化（normalize）逻辑，把 DeepSeek 的模型名强制转换成了 deepseek-chat。

第二步：定位映射逻辑

在容器内搜索 deepseek-chat：

sudo docker exec hermes-hermes-1 grep -rn "deepseek-chat" /opt/hermes/ 2>/dev/null

找到三个关键文件：

文件 作用
hermes_cli/model_switch.py:123 模型切换逻辑，定义了 "deepseek" provider 的默认模型为 "deepseek-chat"
hermes_cli/model_normalize.py:148 模型名规范化函数，强制所有 DeepSeek 模型返回 "deepseek-chat"
hermes_cli/models.py:195 模型描述文件

核心代码在 model_normalize.py：

# 第 148 行
return "deepseek-chat"

这个函数无论输入什么 DeepSeek 模型名，都强制返回 deepseek-chat。

第三步：找到原因

DeepSeek 在 2026 年 7 月 24 日 正式弃用了旧模型名：

旧模型名（已弃用） 新模型名
deepseek-chat deepseek-v4-flash（非思考模式）
deepseek-reasoner deepseek-v4-flash（思考模式）或 deepseek-v4-pro

弃用时间正好是我们配置后就发生的——7 月 23 日部署，7 月 24 日 23:59 弃用生效。所以之前能用，几天后就不能用了。

Hermes 的 model_normalize.py 还在用旧名称 deepseek-chat，导致：

  1. 用户配置 deepseek-v4-flash → 被 normalize 为 deepseek-chat
  2. deepseek-chat 发送到 DeepSeek API → DeepSeek 返回 400 说这个模型名不支持

修复方法

将三个文件中所有 deepseek-chat 替换为 deepseek-v4-flash：

sudo docker exec hermes-hermes-1 sed -i \
  's/"deepseek-chat"/"deepseek-v4-flash"/g' \
  /opt/hermes/hermes_cli/model_switch.py \
  /opt/hermes/hermes_cli/model_normalize.py \
  /opt/hermes/hermes_cli/models.py

重启容器：

sudo docker restart hermes-hermes-1

修复后对话恢复正常。

根本原因总结

这是一个典型的 Provider 端 Breaking Change 未被适配端同步 的问题：

时间线:

  7/23     部署 Hermes，配置 deepseek-chat → 正常工作
  7/24      DeepSeek 弃用旧模型名（生效时间 23:59）
  7/26      Hermes 自动更新配置为 deepseek-v4-flash
            → normalize 逻辑回退到 deepseek-chat
            → DeepSeek API 拒绝
            💥 对话失败

  根因: Hermes 内置的 normalize 映射表未跟上 DeepSeek 的模型名变更

本质上是一个硬编码的映射表过时了。model_normalize.py 将"所有 DeepSeek 模型"强制映射到一个固定值，这个设计在 API 稳定时没问题，但一旦上游改了模型名，就会产生矛盾。

启示

  1. LLM Provider 的模型名不是稳定的 API 契约。DeepSeek 用了一年多的 deepseek-chat 说弃就弃了。
  2. 自动 normalize 逻辑要谨慎。好心帮你"统一名称"的逻辑，在 API 变更时会先于用户配置出错。
  3. Docker 容器内的 Python 代码可以直接修。docker exec + sed 是临时修复的有效手段，但要等上游发新镜像才能永久解决。
  4. 看日志第一行很重要。Normalized model ... to ... 这个看似无害的日志，其实直接暴露了问题所在。
